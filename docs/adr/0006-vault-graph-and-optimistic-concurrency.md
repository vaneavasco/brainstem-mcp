# ADR 0006 — Vault graph in memory, content-hash concurrency, transaction journal

Date: 2026-08-30 · Status: accepted

## Context

Phase 4 (`docs/superpowers/specs/2026-08-30-phase-4-vault-graph-and-safety-design.md`) teaches the server the vault's link/tag graph (`vault_links`, `vault_tags`, `vault_outline`, orphans/hubs) and makes concurrent writes safe: several Claude surfaces (claude.ai web, Claude Code, a second chat) can hold a stale copy of the same note and each `vault_write`/`vault_edit` would otherwise win silently. Two design questions this raised — where the graph lives, and what a write compares against to detect a stale copy — are recorded here, plus the transaction journal and its concurrency model.

## Decision

**The vault graph is derived in memory from `FrontmatterIndex`, never persisted.** `VaultGraph` (`src/vault/graph.ts`) is rebuilt lazily whenever the index's `version` counter changes and answers `resolve`/`outgoing`/`backlinks`/`embedsOf`/`tags`/`orphans`/`hubs` purely from `IndexEntry` data already held in the process (links, tags, headings, block ids parsed once per note by `src/vault/note-parse.ts`). No SQLite, no on-disk graph file. This is single-process, single-vault (ADR 0005) the same way the index itself is: a rebuildable cache, safe to lose at any time, with one source of truth — the files on disk. The ADR 0005 case against SQLite applies unchanged and more strongly here: a synced vault folder (Obsidian Sync, Syncthing, git, Dropbox) can copy a database mid-write, and WAL/SHM sidecar files are not safe under a general-purpose file syncer; a graph that must stay consistent with a folder several tools sync independently is a second source of truth that can drift, for no benefit over recomputing it from the index the process already maintains.

**Optimistic concurrency compares content hashes, not mtimes.** `hash = sha256hex(content)` of the file as read (frontmatter + body). `vault_read`, `vault_batch_read` and `vault_outline` return it; mutating tools accept it back as `expectedHash` and the `WriteGate` (`src/storage/write-gate.ts`) reads the file inside the lock, recomputes the hash, and throws `VaultError('CONFLICT', …, { path, currentHash })` on a mismatch instead of overwriting. mtime was rejected outright: every sync tool this server is designed to sit underneath (Obsidian Sync, Syncthing, git checkout, Dropbox, plus Obsidian's own file-watcher touching files it re-saves) rewrites a file's mtime on events that do not change a single byte — a pull, a re-index, a metadata-only save. A concurrency token that flips on no-op writes would produce false `CONFLICT`s constantly and train the model to ignore them; content hashes only change when the bytes do, and the round trip costs nothing extra because reads already return the hash the model needs to echo back.

**The transaction journal lives under `_brainstem/tx/<txId>/`** — already-reserved, invisible to every tool, as protected as `state.json`. Each entry is `manifest.json` (`id`, `startedAt`, `state`, `ops`, `preimages: [{ path, file }]`) plus one pre-image file per modified/moved/deleted path, written once with `COPYFILE_EXCL` (never overwritten — a stale journal file can never be silently reused). `manifest.json`'s `state` is a three-value machine — `applying` → `applied` | `rolled-back` — and every transition is a fresh write through tmp-then-rename, never an in-place edit: a process crash mid-write leaves either the old state file intact or the new one fully written, never a half-written manifest that could be misread as "committed" or "safe to delete." The journal is deleted only after that terminal state is durably recorded; one left behind (a crash before `applied`/`rolled-back` was reached) is surfaced to the owner in `connection.md` and in the boot log — no automatic replay, because a partially-applied batch with no journal marker for what it intended is exactly the case a human should look at.

**Every mutating adapter call for a path runs inside `WriteGate.withLock(paths, fn)`**, an in-memory `Map<path, Promise>` keyed mutex, sorted paths acquired together so no multi-path operation (a folder move, a transaction) can deadlock against another. A folder move or delete locks the folder path *and* every note/asset path `entriesUnder()` finds already in the index under that prefix — closing the bug where a concurrent write to a file already inside the folder could interleave with the rename and resurrect a folder that had just been removed.

## Consequences

- **Documented residual: a brand-new, not-yet-indexed file cannot be locked by a concurrent folder move.** `entriesUnder()` — and therefore the lock set for `vault_move`/`vault_delete` on a folder — is built from the index, by construction. A file written to disk inside that folder in the instant between its own write starting and the index observing it (chokidar's watch latency, or a write still in flight) is invisible to that lock set. If a folder move runs in that window, the two operations are not serialized: the new file's write can land after the folder has already moved (producing a loud `ENOENT`/`IO` error, not silent data loss) or, rarer, the folder can be recreated under the new file after the move believed it had emptied the old location. This is accepted rather than fixed because closing it fully would mean locking on a real-time filesystem watch rather than the index (a much larger change, in a single-process server where the window is a handful of milliseconds and the failure modes are loud errors, not silent corruption or an unrecoverable state) — a good trade for the deployment target (one owner, not a swarm of writers) but wrong for anything with true concurrent multi-writer traffic. Revisit if that ever changes.
- **`CONFLICT` is a new, load-bearing error code the model must handle**: `expectedHash` is optional everywhere, so today's "last write wins" behavior is unchanged for callers that omit it (existing automations, the reference tool surface). The default instructions (§4.11) tell the model to pass it when it edits a note it read earlier in the conversation, but nothing enforces that server-side — a client that never reads a hash gets no protection, by design (parity with a stateless tool caller that may not track note versions at all).
- **A leftover transaction journal is a manual-intervention signal, not a bug report.** The owner is expected to inspect `_brainstem/tx/<txId>/` (pre-images plus a manifest stuck at `applying`) after an unclean shutdown mid-transaction and decide whether to restore from the pre-images by hand; automatic replay was rejected because a manifest that never reached a terminal state does not by itself say whether apply had partially succeeded on disk, which is precisely the ambiguity a human should resolve with the pre-images in hand.
- **The graph adds memory, not disk I/O**, proportional to link/tag/heading counts already parsed into `IndexEntry`; per the Phase 4 spec's budget, an entry grows from roughly 200 B to 1–2 KB, and the existing 64 MiB index ceiling (`MAX_INDEX_BYTES`, ~30k notes) is the effective cap. Rebuilding the whole graph on every index `version` bump (rather than incrementally patching it) was chosen for simplicity and correctness — the index itself is already lazily rebuilt in the same way, and vault-scale note counts keep the recompute cheap enough that a perf guard (`tests/perf/index-build.test.ts`) exists instead of an incremental-update design.

## Alternatives rejected

- **A persisted graph (SQLite or a JSON sidecar) inside the vault.** Same failure mode ADR 0005 rejected SQLite for: a general-purpose file syncer can copy a database or a large JSON file mid-write and corrupt or split-brain it, and it would be a second source of truth that must stay reconciled with the actual notes — for a data structure that is cheap enough to hold in memory and rebuild by walking the index that already exists.
- **mtime-based optimistic concurrency (`If-Unmodified-Since`-style).** Rejected because the sync tools this server is explicitly designed to run underneath rewrite mtimes on events that never touch note content, which would make `CONFLICT` fire on nothing changing and train the model (or the owner) to stop trusting it. Content hashing is the only signal that tracks the thing that actually matters — did the bytes change.
- **A single global write lock instead of path-keyed locking.** Would trivially avoid every interleaving bug this phase found, at the cost of serializing unrelated notes' writes against each other for no reason — a real cost once `vault_transaction` and multi-note renames are common operations. Path-keyed locking with sorted multi-path acquisition gets the same deadlock-freedom with actual concurrency for the common case (two unrelated notes edited at once).
- **Automatic replay of a leftover transaction journal at boot.** Rejected: a manifest stuck at `applying` does not tell the boot code how far `apply` actually got on disk before the crash, so a blind replay could double-apply an op that had already landed. Logging the leftover journal and leaving the pre-images for the owner is slower but never wrong.
