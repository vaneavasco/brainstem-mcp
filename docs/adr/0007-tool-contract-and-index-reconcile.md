# ADR 0007 — Tool contract (closed inputs, open outputs, bounded results) and index reconcile

Date: 2026-09-20 · Status: accepted

## Context

A set of multi-step questions was given to fresh models that had only this server's tools and a vault of about 37,000 notes, and the answers were checked against the disk. The answers were right; the contract between the server and its clients was not. Four things went wrong, each observed, none hypothetical:

1. A tool argument the server does not declare was dropped without a word. `vault_frontmatter_update { updates: … }` answered ok and changed nothing; `expected_hash` for `expectedHash` switched the concurrency check of ADR 0006 off for that write.
2. Clients cache the tool list. Output schemas were closed (`additionalProperties: false`), so the first result that carried a field added after the client's copy was rejected whole, with "data must NOT have additional properties" instead of an answer.
3. Clients refuse large results outright. One, with a token limit on tool results, took about 51,000 characters and refused (or diverted to a file the model cannot read) 55,100 and 59,800; another accepted 120,000. A refused result is worse than a truncated one: the call is spent and nothing arrives. `vault_batch_read` of a dozen long notes, and `vault_query` over a few hundred rows, both hit it.
4. An external job rewrote about 24,000 files in a minute. The file watcher lost events (an inotify queue holds 16,384) and the index served stale frontmatter until a restart, with no sign of it.

## Decision

**Inputs are closed, at every level.** Every tool input is a `z.strictObject`, and so are the nested `where` conditions, sort keys, tags filters, edit patches, transaction ops, batch items and the `vault_links` filter. An unknown key is an error that names the key. The one exception is deliberate and listed in the test that enforces the rule (`tests/tools/surface.test.ts`): JSON Canvas is extensible by design, so a canvas node, edge or patch may carry properties this server does not know, and they are written through unchanged. `z.record` inputs (`set`, template `vars`) are maps, not objects with named keys, and stay maps.

**Outputs are open, at every level.** Every output schema is a `z.looseObject`: a result may gain a field without breaking a client that validates `structuredContent` against the schema it cached yesterday. A test walks every output schema of every tool and fails on a closed node. Removing or renaming an output field remains a breaking change; adding one is not.

**Results are bounded by characters, as the client receives them, for the strictest client seen.** `CLIENT_SAFE_RESULT_CHARS` is 48,000: below the smallest refusal measured, with a margin because JSON costs more tokens per character than prose. The rule that survived three reviews is *measure, never estimate*: a constant "overhead per note" or "room for the hint" was broken each time by an ordinary input (a 250-character path, a body that opens with line breaks, fifty long column names). So every tool weighs its own result with the lists empty and its longest possible hint in place, and gives the lists what is left (`src/vault/budget.ts`): `vault_query` / `vault_recent` (groups get at most half when rows are wanted too, all of it with `countOnly`; example paths go before groups do; the largest groups survive), `vault_batch_read` (frontmatter gets at most half, the largest blocks are left out and flagged; bodies share the rest in serialized characters, each cut at the longest prefix that fits), `vault_list`, `vault_links` (four lists, short ones first), `vault_tags`, `vault_search_frontmatter`, `vault_analytics_findings`. An argument that is echoed back counts against the result, so it is capped where it is declared: a path 1,024 characters (the path policy's own limit), a heading path, a field name or a tag 200, `select` 50 names, a search string or a glob 1,000. `vault_search` is bounded too: its hits travel twice (`files` groups what `matches` lists flat), so it keeps the longest run of hits whose two renderings fit together. One item that could never fit (a row holding a 100,000-character value) is skipped rather than allowed to hide every item after it. A cut is never silent: `truncated` plus a `hint` that is true for that call and names the narrower call. `vault_read` of a single note keeps its 120,000 ceiling and its `maxChars`: a reader who wants one long note whole can have it from a client that takes it. The complete match set is a different thing from a presented page of it: code that needs every match (`vault_search` narrowing its candidates) calls `matchEntries`, never the rows of `evaluateQuery`.

**The index reconciles itself with the disk.** `FrontmatterIndex.reconcile` compares a fresh listing (size, mtime: no reads for unchanged files) with the index: what differs is re-read, what is new is added, and what is missing from the listing is removed only after its absence is confirmed on disk, because the listing is a snapshot and a tool may write or move a note while the sweep runs. It runs on a timer (`VAULT_RECONCILE_MS`, default 5 minutes, `0` off, otherwise at least 10 seconds) and when the watcher reports an error. A timer tick during a pass is skipped; a watcher error is never dropped, because it means events were lost: during a pass it is answered by one more pass, and within 30 seconds of the end of the last pass by one trailing pass when the gap ends (a watcher that cannot watch reports once per folder, and each pass lists the whole vault). A failed pass is reported without its error text (an fs error carries an absolute path), and `close()` waits for the pass in flight. `brainstem_ping`, `/health` and `./brainstem status` show when the index was last checked. Measured on the 37,000-note vault: an idle pass is one directory walk, about one second, and re-reads nothing.

## Consequences

- **Upgrading to the first release with this contract breaks a cached client once.** A client still holding the previous release's closed output schemas rejects the results that carry a new field by default: `brainstem_ping` (always: `index`), a `vault_search` with zero hits (`hint`), a `vault_query` grouped by a list field or cut by the character budget (`hint`). It also does not see new arguments. Reconnecting the connector refreshes the tool list at once; otherwise the list is cacheable for an hour, and how long a given client really keeps it is the client's business. From this release on the class of failure is gone, which is the point.
- **A caller that relied on a dropped argument now fails loudly.** None was found in this repository (`scripts/`, `src/cli/`, README, llms.txt, docker smoke) nor in the one known external integration; that is what the strictness is for.
- **`vault_batch_read` returns less than before for a batch of long notes** (48,000 characters in all instead of 120,000 of bodies), and may leave frontmatter out. The old budget returned nothing at all to the client that matters most; the intended call for long notes is `sections`.
- **A symlinked note inside the vault** is reachable by path but not part of a directory listing; reconcile keeps it (its absence is never confirmed) at the price of one re-read per pass; a symlinked asset costs one `stat`. Not worth special handling until someone has many.
- **A file that could not be indexed is remembered by size and mtime** and not read again until one of them changes. A tool that repairs such a file while preserving both (same byte length, mtime restored) stays invisible to reconcile until the watcher or a restart sees it. Accepted: the alternative is a full read of every broken file on every pass.
- **The guarantee covers results that are lists; a tool that returns one document is bounded by the document.** `vault_read` and `vault_daily_note_read` (120,000 characters, `maxChars`), `vault_outline` (a note with thousands of headings), `vault_canvas_read`, and the dry-run diffs of `vault_edit` and `vault_transaction` can exceed what the strictest client accepts, by as much as the document or the caller's own patch is large. They are exempt on purpose: the reader asked for that document, and `vault_outline` plus `section` is how to read a long one in parts. Characters that JSON escapes (a body of control characters) make a 120,000-character read several times larger on the wire; nothing realistic does.
- **A reconcile pass has no timeout.** On a filesystem that hangs, a pass never settles, later triggers only queue, and `close()` waits with it. The same hang stalls every tool call on that vault, so a timeout here would be the least of the problems; noted rather than built.
- **Reconcile is not a substitute for the watcher.** Between two passes the watcher is still what keeps the index current; reconcile bounds how long a lost event can matter.

## Addendum (same day): what the index holds, and a budget that speaks

Profiling the 37,000-note vault showed 940 MB of heap after indexing 264 MB of notes. The cause is a V8 property, not a leak in the usual sense: a substring (a regex capture, a `slice`, a YAML scalar) is a view into its parent, and the parent stays alive as long as the view does. Every string in an `IndexEntry` was such a view, so the index retained every note it had ever read. `FrontmatterIndex.fromNote` now returns a detached copy (`detached()`: strings of 13 characters or more are re-created, shorter ones are already copies in V8), and `LinkRef.raw` is gone: the link's source text is `text.slice(start, end)` for whoever holds the text, and the one thing link rewriting needed from it (was a markdown target written `<…>`) is the flag `angle`. After: 254 MB of heap for the index, 373 MB with the graph, 0.61 GB resident instead of 1.29 GB. `tests/perf/index-memory.test.ts` measures retention in a child process with an exposed GC, because no assertion on values can see it.

The index byte budget of ADR 0006 (64 MiB, "about 30k notes") had no listener, and could not have reported a vault that was over it at boot, since the index is built before anything can subscribe. `watchBudget` sets the line and the listener and checks at once; the server logs one warning per episode and `brainstem_ping` carries `bytes`, `budgetBytes`, `overBudget`. The line moves to 256 MiB from measurement (3.5 KB per long note, heap about twice the serialized size). It stays a warning: evicting entries would make queries silently incomplete, which is worse than using memory the owner can see. `./brainstem status` prints the warning; `/health` is public, so it carries only the yes/no.

An adversarial review of this addendum, findings proven by running code, found that the copy assigned keys with `out[key] =`, so a `__proto__` key in frontmatter became the copy's prototype (the key vanished and its children answered as fields); that the size was counted in UTF-16 units; that a non-finite budget broke `brainstem_ping`'s output; and, older than this change, that a YAML alias cycle in one note aborted the boot. All four are fixed with a test each, and the reviewer's scripts were rerun against the result. Reading that report turned up one more: field lookup walked inherited properties, so `constructor` was a field of every note. Lookup is own-properties only, in one shared function.

A second round, on the fixes, proved six more. The scale run passed with the retention bug put back (names under 13 characters, which V8 copies, and quoted scalars, already copies): its seed now uses long names and plain scalars, its bounds sit 1.4x above what it measures, and it was run once with the copy disabled to see it fail (11.2 KB of heap per note against a 4.8 KB bound). YAML aliases amplified memory (a 1 MB note, one anchor used 99 times, cost 116 MB; 45 of them stopped the boot): frontmatter is now admitted in one pass where it is parsed (`admit` in `src/storage/frontmatter.ts`), which refuses a cycle through any container, refuses a block whose written-out size passes `MAX_FILE_BYTES`, and turns sets and ordered maps into lists and mappings, memoized per node so a shared node costs once. A single note's frontmatter travelled uncapped in three results; it now gets at most half of `CLIENT_SAFE_RESULT_CHARS` and is otherwise left out and flagged, never cut. And `__proto__` again, twice: a selected column assigned rather than defined, and a `set` key that zod's record drops in silence, so the write reported success having done less than asked; that key is now an input error.
 Every problem of scale so far was found on one real vault after the code had shipped green over a handful of notes. `npm run test:scale` (its own CI step) seeds 40,000 deterministic notes and asserts build time, serialized and heap bytes per note (measured in a child process with an exposed GC), an idle reconcile pass that re-reads nothing, and that every list-shaped tool result fits `CLIENT_SAFE_RESULT_CHARS`. It logs the numbers on every run.
