# ADR 0005 — Single-user state-in-vault, tunnel modes

Date: 2026-08-28 · Status: accepted

## Context

This is a personal tool with one real user (the owner), not the multi-tenant Google-Drive product v1.2 of the plan described. On 2026-08-28 the owner re-scoped the project in conversation: skip multi-tenancy, Google as an identity provider, and Google Drive entirely; get something the owner can actually run today, entirely on their own machine, against their real Obsidian vault. The decisions and their rationale are recorded in full in `docs/superpowers/specs/2026-08-28-single-user-local-tunnel-design.md`; this ADR records the resulting architecture and what it forecloses.

## Decision

- **Single-user Authorization Server + Resource Server, gated by an owner secret.** The server remains its own OAuth 2.1 AS+RS towards Claude (PKCE S256, CIMD with a host allowlist, refresh rotation, `/oauth/revoke`), but there is no second OAuth plane to an external identity provider — the consent page asks for a generated secret kept in `.env` instead of a Google login.
- **All server state lives inside the vault, as JSON, in a reserved `_brainstem/` folder** (`state.json` for OAuth clients/tokens, `connection.md` and `instance.json` for the owner). `_brainstem/` is rejected by the path policy and skipped by every tool, list, search and watch — it is invisible to Claude. Because whatever already syncs the vault (Obsidian Sync, Syncthing, git, Dropbox) now also carries this state, a second machine with the same `.env` resumes with the same clients and tokens.
- **Two tunnel modes, plus `none`.** `cloudflare` mode (a named tunnel via `TUNNEL_TOKEN`) gives a stable hostname that never changes and is the recommended default; `quick` mode needs no Cloudflare account but gets a new `*.trycloudflare.com` hostname on every restart, which a small TypeScript supervisor detects and writes atomically to a file the app watches, restarting itself when the URL changes; `none` skips the tunnel for Claude Code / localhost-only use.
- **A cross-platform TypeScript CLI**, not a shell script and not a web UI, drives `docker compose` and edits `.env` (`setup`, `up`, `url`, `status`, `down`, `logs`, `revoke-all`, `secret`). Node 24 runs the `.ts` files directly.

## Consequences

- **Deferred, not deleted:** multi-tenancy (tenant isolation suite, per-tenant rate limits, audit table, `/account` page), Google as an identity provider (encrypted refresh-token storage, re-auth handling), and the `GoogleDriveAdapter` are all out of scope for this phase. The seams that would let them come back without a rewrite are kept on purpose: `StorageAdapter`, `RuntimeResolver(ctx)`, the `TokenStore` interface, and an AS whose only user-specific piece is `OwnerAuth`. Resuming this path means: swap `FileTokenStore` for a Postgres-backed `TokenStore` (the interface doesn't change), add a Plane B (Google) OAuth client and wire its callback into the existing `/oauth/authorize` continuation, implement `GoogleDriveAdapter` behind the existing `StorageAdapter` interface, and reopen the plan's old Phase 2/3/4 outlines (kept verbatim in `docs/implementation-plan.md` §10 for exactly this reason).
- **Postgres and Heroku are dropped**, not deferred with a seam — there is no per-request database anymore, and self-hosted Docker Compose is now the only supported deployment. Resuming Heroku hosting would mean re-introducing a stateless-per-request server (the current one keeps one boot-time `VaultRuntime` and JSON file state, which does not fit an ephemeral multi-dyno filesystem) — a bigger step back than the pieces above.
- **A stolen `.env` is full access**, same as any self-hosted secret; there is no rotation of it that doesn't require restarting the app. `npm run brainstem -- secret rotate` mitigates by also revoking every outstanding token in the same step.
- **Quick-tunnel URL rotation is a real, expected failure mode**, not a bug: every restart in `quick` mode invalidates the OAuth issuer for existing tokens (401 on the next request), and the connector must be removed and re-added by hand because the URL is part of the connector's own identity in claude.ai and Claude Code. `cloudflare` mode exists specifically to make this a non-issue.

## Alternatives rejected

- **A hosted CIMD + Google-token-vault provider** (WorkOS AuthKit + Pipes, Scalekit MCP Auth, Descope, Auth0 Token Vault) — every option requires an external SaaS dependency even for local development and moves custody of the user's own credentials to a third party, which directly contradicts "everything runs on your machine." See the build-vs-delegate table in `docs/reviews/2026-08-28-auth-consistency-review.md`.
- **Better Auth's self-hosted `mcp()` + `@better-auth/cimd` plugin** — would have saved roughly a day of AS/RS work, but it pins `legacy: 'reject'` (Claude's 2026-07-28 rollout isn't there yet), is Next.js-centric, forces session-cookie consent to be worked around per client, and pulls in a large security-core dependency for behavior we can implement fail-closed ourselves in a few hundred lines. Same review as above.
- **SQLite in the synced vault folder** — rejected outright, not merely deprioritized: SQLite's WAL/SHM sidecar files and mid-transaction states are not safe under a general-purpose file syncer (Obsidian Sync, Syncthing, Dropbox), which can copy a database mid-write and corrupt it. If a future machine-local cache ever needs SQLite, it must live outside the vault. Plain JSON, written temp-file-then-rename, has no such failure mode because a syncer only ever sees a complete file.
